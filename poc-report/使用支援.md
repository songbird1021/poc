# 使用支援：遇到需要時再看

本手冊沒有新增測試。版本、命令與時間預算以主方案為準。

## 1. 怎樣把「好像說了什麼，又沒說清楚」變成可展示的觀察

以下是虛構示例，**不是公司程式規則，也不能填入實測結果**。

| 回答形態 | 示例 | 如何記錄 |
| --- | --- | --- |
| 概括功能 | 「系統會檢查 Golden 是否符合資格。」 | 沒指出條件與位置，記「僅概括」 |
| 具體但未查核 | 「符合 `status == READY` 才可選。」 | 能查核，但目前仍「未確認」 |
| 有實作依據 | 「在某函式的某分支，條件不符時回傳 disabled；有對應片段。」 | 人工確認片段支持後記「支持」，註明適用分支 |
| 業務理由推論 | 「這樣設計是為了避免品質風險。」 | 沒有需求／規格／其他依據就保留為推論 |

報告可用句型：

> 這段描述提供了功能概覽，但沒有列出影響可選狀態的條件。條件是在後續回 source 查核時才取得。因此，這次產物對【實際有幫助的部分】有用，對【缺少的部分】仍需額外調查。

不要只用「不夠 promising」當結論；保留一段回答、一段來源與缺少的資訊，主管才看得懂你的判斷。

## 2. 查核時容易遇到的情況

- **引用路徑不存在：**保存原引用，記「來源無法定位」。不能直接把整個答案都判錯，也不能讓 agent 的自我保證替代來源。
- **條件可能在 UI、API、後端多處：**請把來源與層次寫清楚。只查到其中一處時，不宣稱列出了所有原因。
- **只有程式行為，沒有設計原因：**可以確認目前怎麼運作，原始業務理由標未知。
- **工具與 baseline 答案相同：**先看來源和人工補查負擔；沒有可確認差異就寫「此案例未觀察到明確額外效益」。
- **記憶保存成功，但新 session 沒讀：**分開記「保存成功」「本輪未取回」，不要合併成全成功或全失敗。
- **圖或 dashboard 很漂亮：**截與本案例相關的一小塊，旁邊標出它實際回答了什麼；全域圖只作背景。
- **中文查詢找不到節點：**正式 prompt 保持三組一致。工具若改用程式中的英文識別字查詢，記錄為查詢展開；自己提示新關鍵字則算人工介入。不要只替其中一組偷偷加入答案線索。

## 3. Token 只拿得到一部分時怎麼辦

先保存原始用量畫面或文字，標記是 session 累計、單輪還是其他範圍；缺少欄位填 NA。

- 只有整個 session 用量：記整題合計，無須硬拆 R0、R1。
- 有兩個累計快照且統計範圍相同：可用 R1 後減 R0 後取得追問增量。
- 不確定是否含子代理或外部模型：註明範圍未知，不宣稱完整成本。
- 沒有可比數字：投影片不放 token 比率，仍可呈現查核品質與操作負擔。

初始建置成本和每次查詢成本分開列。本次沒有足夠重複樣本時，不推算「用幾次一定回本」。

## 4. 主管可能會問的問題

下列是答題結構，請填自己的證據，不能直接假裝已有結果。

**「所以最後要用哪個？」**

> 就【此案例】而言，我觀察到【證據】。目前建議【暫用某流程／做一個補充案例／暫不增加工具】，主要待確認的是【單一問題】。

**「Claude Code 本身不就能做？」**

> 所以我保留了直接使用 Claude Code 的比較。這次想知道的是現成工具在保存、取回與維護分析結果上增加了什麼；本次觀察到【差異／尚無明確差異】。

**「為什麼不直接寫文件？」**

> 維護筆記是合理選項。我的出發點是希望借用現成格式、目錄與更新機制；這次沒有設人工文件對照組，所以還不能說工具一定更好。此次先確認了【工具提供什麼／仍需維護什麼】。

**「省多少時間或 token？」**

> 我有【可取得資料】，但【量測限制】。這次主要證據是【具體工作結果與補查負擔】，尚不足以推估長期節省比例。

**「能自動學會我們的業務嗎？」**

> 我分開看既有產物重用、新結論保存、過時內容更新。這次實際驗證了【項目】，尚未驗證【項目】；保存問答本身不會證明業務結論正確。

**「沒有效果，這幾天有什麼收穫？」**

> 我們確認了【具體缺口或環境限制】，因此可以避免在【缺乏證據的方向】繼續投入；下一步聚焦【有理由的小動作】。

## 5. 給其他 AI agent 的交接提示詞

等到要整理結果時才使用。在公司允許的環境提供資料；不用將整個 codebase 當成整理報告的必要輸入。

```text
請協助整理這次三天研究報告。先閱讀主方案、環境紀錄、findings.md、
claims.md 與已完成的 runs；尚未提供的資料請列為缺漏。

核心動機：Claude Code 在不同 session 反覆探索局部 codebase；
我想確認現成工具能否提供保存、組織、重用、更新理解的方式，
以及產物是否足以回答真實業務條件。選型以開源、公司可使用為主。

規則：
1. 舊 ChatGPT 建議不是定案。工具 README、模型自述與人工查核結果分開。
2. 待填欄位、模板示例、功能宣稱不能寫成實測結果。
3. 不補造 token、時間、正確率或已完成測試。
4. 沒有人工文件對照組，不能宣稱勝過手工筆記。
5. 新 session 讀到舊圖，不等於學到上一輪新發現。
6. 不新增測試；先用已有證據完成報告。

請輸出：三項以內主要發現、一項有依據的下一步、
五頁英文投影片文字與中文講稿。每項結果標記 evidence ID 或 run 來源。
若資料不足，縮小結論並指出缺漏，保留未知。
```

## 6. 報告整理完成前，最後看三件事

1. 每項「我們發現」都有對應 run 或 evidence；文件功能用「官方提供／描述」表達。
2. 投影片中的下一步只選一個，不把所有未測項目都變成承諾。
3. 能用一句話說清楚：工具提供了什麼，以及你還需要做什麼。
