對，你這個修正比較準。

**Understand Anything 不是沒有嘗試理解 business meaning。** 它的 `/understand-domain` 本來就是把 code 結構、entry point、摘要等丟給 LLM，讓 agent 推理出 `domain → flow → step`，甚至 business rules。也就是說，它確實是在做「從 code 推 business semantics」，只是你的實測感受是：**有推理、有產物，但離一個工程師真的能信任並拿來工作，還有落差。** :chatgpt-content-reference{index="0"}

我覺得這個 distinction 很重要，因為你 1-1 可以說：

> 不是 knowledge graph 做不到 business logic，而是目前 business logic 很大部分仍然是 LLM inference；當 source evidence 只有 code 時，它能推到某個程度，但對歷史背景、特殊 business rule、設計理由的掌握有限。

而你們**已經有文件**這件事，反而讓下一步變得更有意思。

## 可以把文件一起餵嗎？

**可以，而且我認為這比繼續研究 graph visualization 值得。**

但不同工具「code + docs」整合程度差很多。

### Understand Anything：能讀文件，但目前比較像兩套 graph

現在 Understand Anything 有 `/understand-knowledge`，可以把 Markdown knowledge base 分析成 knowledge graph，LLM 會抽 entity、claim、implicit relationship 等。README 也直接定位成可以處理 codebase、knowledge base 或 docs。 :chatgpt-content-reference{index="1"}

不過有一個你需要注意的限制：

目前 **codebase graph 和 knowledge graph 並不是很完整地融合成一個 unified model**。

它的 `/understand` 產 code graph，`/understand-knowledge` 產 knowledge graph；官方設計文件甚至寫到兩者會寫同一個 `knowledge-graph.json`，跑其中一種會取代另一種。 :chatgpt-content-reference{index="2"}

而 `/understand-domain` 的主要 context 目前還是：

> code file tree + entry points + imports/exports + snippets + project metadata/README

或既有的 code knowledge graph，再交給 LLM 做 domain analysis。它不是明確在做：

> **code evidence + project docs + ADR + old spec → 綜合判斷 business flow** :chatgpt-content-reference{index="3"}


所以如果你想的是：

> 「我們有 20 份 project docs，能不能讓 UA 同時看 docs 和 code，告訴我目前真實的 business logic？」

**我目前不會把 Understand Anything 當成這個 use case 已經做得很成熟。**

---

### 反而有些新工具正在往這個方向做

例如我前面提到的 Repowise，現在的設計明顯比較接近這個問題。

它除了 code dependency graph，還會看：

**git history + ADR + PR body + code comments + 人工 decision records + generated docs**。

而且它允許你指定像 `docs/ARCHITECTURE.md`、`docs/runtime-flow.md` 這類檔案作為 synthesis 的額外 evidence。 :chatgpt-content-reference{index="4"}

更有意思的是，它現在甚至有 **documentation drift**：

> 拿你自己的 Markdown 文件裡面的 claim 去跟現在的 code tree 對，看哪些說法已經被 code 推翻。 :chatgpt-content-reference{index="5"}


這其實剛好打到你講的：

> 「我們有文件，但可能沒有維護、可能過時。」

我覺得這才是很有意思的方向。

---

# 「文件可能過時」其實不是 blocker

反而可以變成一個更好的問題。

你不要把文件當 **truth**。

把它當成 **另一個 evidence source**。

比如：

```text
Source A — current code
Payment retry = 3 times

Source B — architecture doc, 2023
Payment retry = 5 times

Source C — git commit, 2025
"Reduce payment retries from 5 to 3 because ..."

→ Current behavior: 3
→ Historical intent: originally 5
→ Reason for change: ...
→ 2023 document is stale
```

**這才是我覺得理想的 legacy-code intelligence system 應該做到的事情。**

不是把 README 全塞給 LLM，然後相信它融合出來的答案。

而是答案最好能分：

- **現在 code 顯示什麼**
- **文件說什麼**
- **git/history 說為什麼變**
- **兩邊是否衝突**
- **哪些是 LLM 推論**
- **哪些是直接 evidence**

這樣信任度會高很多。

---

## 這其實也給你一個很好的「下一步」

我現在反而覺得你不需要急著做一個很大的 benchmark。

挑你們一個 subsystem，找：

**code + 2～5 份既有文件**。

最好故意包含一份你知道有點舊的。

然後測幾個問題：

> 「文件描述的流程跟現在 code 是否一致？」

> 「有哪些文件裡的 behavior 現在已經不是這樣？」

> 「這個 business rule 是只有 code 看得到，還是文件也有？」

> 「這個 exception 為什麼存在？文件、git history、code 各提供了什麼資訊？」

這個 experiment 比：

> Understand Anything graph 好不好用？

更有價值。

因為你的問題已經進化成：

> **只從 code 推 business meaning 效果有限；那如果加入既有 organizational knowledge，能不能讓 AI 的理解更完整，而且還能辨認 stale knowledge？**

這是一個非常合理的下一步。

---

而且我覺得這會讓你跟主管的 story 更漂亮：

**一開始**

> 想把 code 自動整理成 business knowledge。

**試 UA 後**

> 發現它確實用 LLM 嘗試從 code 推 business semantics，但僅靠 code inference 效果有限。

**新的觀察**

> 其實公司不是完全沒有 knowledge，而是 knowledge 散落在 code、舊文件、git history 和人的腦袋裡。

**所以新的方向**

> 與其追求「AI 從 code 自動猜出所有 business logic」，更合理的問題可能是：  
> **能不能把 code + existing docs + history 合在一起，並且知道哪些資訊可信、哪些已經 stale？**

我覺得這個 learning 比「UA 不好用」強很多。

而且坦白說，**這已經開始接近真正的問題了**：你缺的不是 code visualization，而是 **evidence-backed organizational knowledge layer**。
