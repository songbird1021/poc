## 為什麼我現在特別注意 Unblocked

你前面說的一句話，其實跟它產品定位幾乎完全重疊：

> 「我們有些專案文件，但不一定有維護，可能過時。」

Unblocked 不只是把文件丟進 RAG。

它現在的設計是把：

**source code + PR + Slack/Teams + Jira/Linear + Confluence/Notion/Google Drive + incidents/production**

放進同一個 context layer。官方文件明確說它會跨 source reasoning，而不是一個個 source 分開搜尋。:chatgpt-content-reference{index="0"}

更重要的是，它直接把你剛才問我的問題當產品問題：

> Markdown 會 stale，不同 source 會互相矛盾，光「能搜尋到」不夠。

它宣稱會依據 **recency、authority、proximity** 去 reconcile conflicting sources，而且回答會附原始 source link。:chatgpt-content-reference{index="1"}

甚至官方 FAQ 說，當 code 和其他來源衝突時，它會把 **main branch 當 source of truth，production code 優先**。:chatgpt-content-reference{index="2"}

這跟 UA 差異非常大。

UA 比較像：

> Code → structure → LLM → 推一個 business model

Unblocked 比較像：

> Code 現在這樣做  
> + 2024 PR 當初為什麼這樣改  
> + Jira 原始需求  
> + Slack 當時討論  
> + Confluence 舊文件  
> → LLM 幫你 reconcile 成答案，並告訴你 evidence 在哪。

**這才是我現在認為最接近「理解公司 business logic」的產品形態。**

---

### 而且它問的問題，跟你的問題幾乎一模一樣

官方直接列出的 use cases 包含：

> Why does this service use Kafka instead of RabbitMQ?  
> Has anyone tried this migration before?  
> Is there an existing implementation I should follow?

回答會考慮 code、internal discussions 和 documentation。:chatgpt-content-reference{index="3"}

也就是它沒有假設：

> 「business meaning 一定藏在 code 裡。」

而是假設：

> **business meaning / technical intent 散落在整個公司的 engineering history 裡。**

我覺得這個 assumption 比 UA 合理很多。

## 有沒有人真的拿 legacy code 用？

有一些滿貼你的案例。

Webflow 把它接到一個 **10+ 年的 codebase**，他們的 engineering productivity 團隊表示，過去 agent 可以看到 repo，但不知道「為什麼 code 會長這樣」；加入 Unblocked 後，會把 Slack、PR、過往 reliability/security decisions 等 context 帶給 Claude/Cursor/Codex。這是 Unblocked 自己發布的 customer case study，所以不能當成獨立研究，但至少是實際公司 deployment，不只是 demo。:chatgpt-content-reference{index="4"}

另一個案例更像你現在的情境：RB Global 有一個新 platform team 要接手 consultant 留下來的 stack，知識散在 GitHub、CircleCI、Confluence、Jira、Slack。官方案例稱原本估六個月的 ownership transition，最後三個月完成，現在支援 200+ developers。依然是 vendor case study，要打折看，但 use case 高度 relevant。:chatgpt-content-reference{index="5"}

## 第三方評價呢？

這裡我就會保守很多。

G2 現在只有 **2 篇 pricing page 可見 review**，所以 4.9/5 完全不能當大樣本證據。:chatgpt-content-reference{index="6"}

不過其中一位 mid-market engineer 提到的優點恰好是：

他也提了一個**非常重要的缺點**：

> 有時會找到一個後來已被推翻的 decision，卻沒有正確標成 stale，所以重要結論仍需要 sanity-check。 :chatgpt-content-reference{index="7"}


這個負評我反而很在意。

因為它證明就算產品說有 recency/conflict resolution，**現實還沒有完全解掉 stale knowledge 問題。**

所以不要期待：

> 接上 Unblocked → 公司知識瞬間變成真理資料庫。

但至少它**正在直接解你碰到的問題**。

# 那 Repowise 呢？

我會把它放在非常清楚的位置：

### 如果你要「自己今天就能 local 跑」：

**Repowise 是我最想測的。**

它會 index：

> code + dependency graph + git history + tests + documentation + decisions

並提供 cited answers。:chatgpt-content-reference{index="8"}

而且它特別有 `get_why()`：

> 找 architectural decisions → evidence → supersession chain；沒有 decision 就退回 git archaeology。

這比單純 code graph 更接近你要的「why」。它也會標 decisions 的 evidence/confidence，並處理 supersedes / conflicts 等關係。:chatgpt-content-reference{index="9"}

優點是：

**local、self-hosted、你可以很快裝來試。**

缺點就是我們剛剛聊過的：

**AGPL**，以及它主要還是 **repo-centric engineering intelligence**。

如果真正的答案在：

> Jira ticket + Slack thread + Confluence 文件

Repowise 的 scope 就沒有 Unblocked 那麼完整。

# DeepWiki 呢？

DeepWiki 是另一個值得認識的 baseline。

它現在會自動把 repository 產生：

**architecture diagram + wiki/docs + source links + Q&A**

而且可以用 `.devin/wiki.json` 告訴它「哪些 business/domain 特別重要」，避免大型 repo 自動分析漏掉重要部分。:chatgpt-content-reference{index="10"}

但本質仍然比較偏：

> **理解 repo。**

而不是：

> **理解 organisation 為什麼把 repo 寫成這樣。**

所以如果你覺得 UA 是「有圖、有描述，但還是不知道 why」，我不會期待 DeepWiki 徹底解決這件事。

---

# Swimm 其實也很有意思，但完全是另一種產品

Swimm 現在已經轉得滿 enterprise modernization 了。

他們的論點甚至跟我們這串聊天的結論非常像：

> deterministic analysis alone misses intent；AI alone hallucinates；所以 deterministic analysis + GenAI + senior engineers 一起做。

他們會交付 architecture/dependency map、critical flow、extracted business logic、knowledge base，而且 SME 會人工驗證。:chatgpt-content-reference{index="11"}

這可能真的比較能把 legacy business rules 挖出來。

但它已經不是：

> 「我裝一個工具玩看看。」

而比較像：

> **「公司要做 legacy modernization project，找 vendor 進場。」**

所以跟你現在 1-1 的探索階段不太匹配。

**Understand Anything → Unblocked**

這兩個剛好可以驗證兩個完全不同的 hypothesis：

**UA hypothesis**

**Unblocked hypothesis**

> 可能不是 code 不夠，而是 business meaning 本來就不只存在 code 裡；如果把 docs + PR + Jira + discussions 一起給 AI，效果會不會明顯提升？

這是一個非常漂亮的第二個 experiment。
